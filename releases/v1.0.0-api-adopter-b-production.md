## Adopter B wiring (host side)

```ts
// apps/adopter-b-frontend/src/training.ts
import {
  RemoteContentSource,
  pinsBundleValidator,
  localStoragePersistence,
} from '@in-app-training/sdk';
import { createContentClient } from '@in-app-training/api-client';

const client = createContentClient({
  baseUrl: 'https://internal-training-api.adopter-b/training/v1',
  token: () => adopterBAuth.currentAccessToken(),
});

export const source = new RemoteContentSource({
  product: 'adopter-b',
  client,
  persistence: localStoragePersistence(),
  validate: pinsBundleValidator(),
  bootBlocking: false, // Adopter B tolerates one refresh cycle of staleness on cold boot; prefers a snappy first paint.
});

source.on((event) => {
  if (event.name === 'content_bundle_update_failed') {
    adopterBErrorTracker.notify(event.payload);
  }
});

await source.start();
```

Adopter B leaves `bootBlocking` off (unlike Reports/Adopter C) because their app-shell is heavier and they prefer serving from the persisted cache while the fresh fetch completes in the background. The Sprint 19 retro documents this as the emerging pattern: pins-heavy hosts with a warm cache pick non-blocking; hosts where the pin set changes daily (Reports') pick blocking. Neither is wrong.
