# v0.5 Kickoff — Pins + Goals

**Sprint 08 · T-096 · The doc Sprint 09 picks up cold.**

## Scope

Two new experience types + one instrumentation primitive:

1. **Pins** — persistent, anchored highlights that live on the page even when no tour is running. Point at "the thing," name it, optionally link to a hint.
2. **Goals** — post-tour conversion tracking. Declares "this tour was worthwhile if the user reaches state X within window Y."

Plus the second-product adoption track — see [`adopter-scouting.md`](adopter-scouting.md) (T-095 output) for who and when.

**Sprints 9–10 covers Pins.** **Sprints 10–11 covers Goals.** Adopter #2 integration lands opportunistically inside those sprints when the second product's `data-tour` PR merges.

Everything else on the v0.5 line (Banners, Launchpad, NPS, Surveys, Webhooks) was HELD or DROPPED at the v0.1.0 retro — see [`../releases/v0.1.0-retro.md`](../releases/v0.1.0-retro.md) `## v0.5 promotion decision`. Do not silently promote them. Reopen only if a specific product owner asks.

## Non-goals

- **No banner / launchpad / NPS / survey / webhook code this cycle.** These stay HOLD.
- **No new content authoring surface** beyond the schema fields the two features add. Pins get authored as JSON alongside tours; Goals get declared inline on the tour.
- **No visual admin authoring UI.** Author velocity is still fine per the retro (5 tours in 2 days). Reopen only if that changes.
- **No mobile support** (still no mobile product). No SSR (host products are all client-rendered).
- **No breaking changes to v0.1 or v0.2 APIs.** Everything additive.

## Feature 1 — Pins

### Motivation

3 of 4 rewrites from the v0.1.0 5-user test were essentially "the checklist would work better if it could point at the CTA the user is trying to find." Tours are transient by design; a Pin is a durable answer to "which button?"

### Shape

Pins live on the page as a small anchored dot / pulse on a `data-tour` target. Click the dot → a compact popover explains the element. The pin itself is dismissable per-user (localStorage-backed like tour completion state).

### JSON authoring surface

New content file type: `*.pins.json`.

```jsonc
{
  "schemaVersion": "v1",
  "product": "example-app",
  "pins": [
    {
      "id": "share-workflow-button",
      "target": "[data-tour=\"workflows-canvas-share-button\"]",
      "title": "Share this workflow",
      "body": "Click the paper-plane icon to hand a workflow to a teammate.",
      "learnMoreUrl": null,
      "audience": ["plan:enterprise"],
      "dismissible": true,
      "showUntil": "2026-12-31"
    }
  ]
}
```

Field notes:

- `target` — same `data-tour` contract as tours. Same CI validation.
- `title` + `body` — support `LocalizedString` from day one (mirror the tour schema).
- `learnMoreUrl` — optional external link, opens in a new tab.
- `audience` — same array shape as tour `audience`. AND semantics, `!` negation. Filters at render time.
- `dismissible` — default true. `false` for compliance/safety pins the host does NOT want the user to hide.
- `showUntil` — optional ISO date. After it, the pin doesn't render. Useful for time-boxed announcements.

### API surface

React:

```tsx
import { PinsProvider, Pin } from '@in-app-training/react';

<PinsProvider pins={exampleAppPins}>
  {/* app */}
</PinsProvider>

// Anywhere in the app (usually not needed — pins auto-render at their targets):
<Pin id="share-workflow-button" />
```

Under the hood, `PinsProvider` mounts a portal that iterates `pins`, filters by audience/showUntil/dismissed-state, resolves each target via `waitForElement` (reuses tour targeting from v0.1), and renders a small anchored dot bound to the target's client rect. Re-anchors on resize + on target-mutation via `MutationObserver`.

Vue: full API parity — `<PinsProvider :pins="pins" />` + `<Pin id="..." />`.

### Analytics

Two new events land in the dictionary (T-090 picks them up on regeneration):

- `pin_shown` — first time the pin renders for a given user.
- `pin_dismissed` — user clicked the dismiss X.

Both gated by `consentCategory: 'functional'` per ADR-0006 defaults.

### Success criteria (measured 30 days after Pin ship)

- **≥ 3 pins live in the example app.** Curriculum author has authored a Pin file the same shape as the existing tours.
- **Pin dismissal rate < 40%.** Higher means we're being noisy; content needs pruning.
- **Zero P0 bugs.** Zero support tickets tagged "pin" beyond baseline noise.
- **Anchoring stays correct across the 3 layout breakpoints** the host product uses. Manual QA on staging + on a real production tab.

### Sprint 9 shape

- **Day 1:** Pin schema (`packages/core/src/schema/v1.ts` — new `PinSchema` + `PinsFileSchema`, additive). Zod, `validate:content` picks up `*.pins.json` alongside `*.tour.json`.
- **Day 2:** Core anchoring logic — reuse `waitForElement`, add a `PinAnchor` that owns positioning + MutationObserver. No UI yet.
- **Day 3:** React `PinsProvider` + `Pin` component. Portal, dismissal, localStorage persistence for dismissal state (key: `in-app-training:pins:dismissed:<id>`).
- **Day 4:** Vue parity port. Same test parity as v0.1's React/Vue split.
- **Day 5:** Analytics events wired + event dictionary regenerated (CI check catches drift). Tests for schema + anchoring + provider.
- **Day 6:** Author 3 real the example app pins from the v0.1.0 retro's rewrite themes. Deploy to staging.
- **Day 7:** Manual QA at 3 breakpoints + 30-min watch after production deploy.

### Sprint 9 non-goals

- No pin-triggered tours. If a pin should launch a tour, v0.6.
- No pin analytics dashboard. Numbers land in PostHog; hosts read them there.

## Feature 2 — Goals

### Motivation

The v0.1.0 retro's #2 surprise: `create-project → user-menu` step drops 12 points, hypothesis is users open a project mid-tour and never come back. Today we can measure that they dropped off *the tour*; we can't measure whether that drop was *good* (they went to do the thing) or *bad* (they abandoned entirely). Goals gives us the second question's answer.

### Shape

A Goal declares "tour T is successful if analytics event E fires within N minutes of `tour_started`." The SDK doesn't observe user behaviour directly — it composes with the host's existing analytics.

### JSON authoring surface

Additive on the tour:

```jsonc
{
  "id": "example-app-onboarding",
  // ...existing fields...
  "goal": {
    "event": "exampleapp.project_created",
    "windowMinutes": 30,
    "match": { "source": "onboarding-tour" }
  }
}
```

- `event` — event name in the host's analytics namespace. Not one of the SDK's own events — this is what the host emits for their own conversions.
- `windowMinutes` — how long after `tour_started` the goal event still counts. Default 60.
- `match` — optional property filter. Goal only counts if the emitted event's properties are a superset of `match`.

### API surface

Zero new host code required at first. The trainer observes goal-configured tours via a new `GoalsSink` on `TrainerConfig`:

```ts
new Trainer({
  // ...
  goals: {
    /**
     * Called when the trainer wants to know if the goal has fired.
     * Host wires this to whatever their analytics sink stores.
     */
    hasEventOccurred(event: string, match: Record<string, unknown>, sinceIso: string): Promise<boolean>;
  },
});
```

Rationale: PostHog / Amplitude / Mixpanel all expose different query surfaces; the SDK doesn't want to know. The host implements one function.

We ship reference `hasEventOccurred` recipes in `docs/wiring-goals.md` for PostHog and Amplitude (10 lines each; both do exactly this query).

### Emitted event

- `tour_goal_reached` — payload `{ tourId, event, matchedAt }`. Fires on the first affirmative `hasEventOccurred` inside the window.
- `tour_goal_missed` — payload `{ tourId, event, windowEndedAt }`. Fires once at window end if no affirmative.

Both land in the event dictionary via T-090.

### Success criteria (measured 30 days after Goals ship)

- **Onboarding goal reached rate ≥ 45%.** Baseline unknown; this is a placeholder — first sprint of data sets the real target.
- **`create-project → user-menu` mystery resolved.** The retro hypothesis was that non-completers who dropped there actually went and did the thing. Goal firing on `exampleapp.project_created` within 5 minutes of drop confirms or refutes.
- **Zero double-count** — replaying the same event twice must not fire the goal twice for the same tour instance.

### Sprint 10–11 shape

- **S10 D1:** Schema `GoalSchema` + attach to `TourSchema`. Validation.
- **S10 D2–3:** Trainer wiring — after `tour_started`, register a check that polls `hasEventOccurred` at a sensible cadence (default 60s; capped total polls) until match or window expiry.
- **S10 D4:** Emit `tour_goal_reached` / `tour_goal_missed`. Dedupe per `(tourId, tourStartTimestamp)`.
- **S10 D5:** `docs/wiring-goals.md` with PostHog + Amplitude recipes.
- **S11 D1–2:** Wire the goal on the example app onboarding tour (against `exampleapp.project_created`). Deploy to staging.
- **S11 D3:** 7-day metrics; answer the retro's hypothesis in the Sprint-11 retro.

### Sprint 10–11 non-goals

- No goal analytics dashboard (numbers in PostHog).
- No multi-goal-per-tour. One tour = one goal, for now.
- No polling behaviour customisation. The 60s cadence and window-expiry-triggered final check are enough for MVP.

## What this v0.5 does NOT do

- **Does not ship banners.** No product asked.
- **Does not ship launchpad, NPS, surveys, webhooks.** Same reason.
- **Does not build a training dashboard.** That's Sprint 18–20 per ROADMAP.md.
- **Does not touch the v0.1 API contract** — every change is additive schema or new module.
- **Does not gate itself on the second-product adoption.** If Adopter Product A or Adopter Product B are ready, they get Pins + Goals; if not, the example app gets them first and the second product opts in later.
