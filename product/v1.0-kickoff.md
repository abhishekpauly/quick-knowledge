# v1.0 Kickoff — REST API + hot content + third adopter

**Sprint 15 · T-222 · The doc Sprint 16 picks up cold.**

## Scope

The v1.0 tier turns the SDK from "shipped on three products" into "safe for any host to adopt". Four line items, roughly one per sprint slot in the 15–20 window:

1. **Public REST API** — ADR-0007 accepted this sprint. First endpoints (`GET /content/:product` + ETag) land in Sprint 16.
2. **Content served from API** — hot-updates without redeploy. ADR-0008 in Sprint 16, SDK integration in Sprint 17.
3. **Third adopter (Reports)** — React, target Sprint 17. `data-tour` PR expected end of Sprint 16.
4. **Cross-product analytics dashboard** — deferred to Sprints 18–20 per ROADMAP. Retool/Metabase, not a rebuilt Amplitude.

The two compliance code drops (`Trainer.forgetUser()` and `ConsentAdapter`) already landed in Sprint 12 — pulled forward because both ADRs were design-locked and the code was small. They do **not** need a v1.0 slot.

## Non-goals (unchanged from Sprint 14 T-211)

- **No hosted authoring UI.** JSON via git PR is still faster than WYSIWYG for the technical author. Reopen only on the specific trigger from `product/vs-appcues.md`.
- **No analytics query API.** Every host emits to PostHog / Amplitude / Mixpanel; rebuilding the query surface duplicates infra.
- **No user CRUD endpoint on the REST API.** The API's `users:*` scope is delete-only (`POST /users/:userId/forget`). Anything else belongs in the host's IAM.
- **No mobile SDKs.** Still no mobile products. Non-goal remains a non-goal.
- **No Banners / Launchpad / NPS / Surveys / Webhooks code.** Launchpad + NPS + Surveys DROPPED at Sprint 14 T-211. Banners + Webhooks stay HOLD.

## Adopter posture

- **Adopter Product A** (React) — no changes expected. Will opt in to hot-updates when Sprint 17 lands, at their pace.
- **Adopter Product B** (Vue, Pins-only) — same. Their Pins bundle becomes the first "publish via API" candidate because pin copy edits are the most frequent request they've made.
- **Adopter Product C** (Reports, React) — new in Sprint 17. Onboards on the same content-in-git path v0.5 uses, then migrates to content-via-API in Sprint 18 as the smoke test for the migration path.

## What the v1.0 team must NOT rediscover

Repeated once here so the debate stops recurring inside sprints:

- Mobile is a non-goal until a real mobile product commits.
- The visual authoring UI is a non-goal; JSON is faster for our author.
- Multi-channel workflow orchestration is Braze/Iterable territory.
- Analytics Studio is Amplitude/PostHog territory. Only the cross-product aggregator is in scope.

If any of the above becomes urgent, that's an ADR of its own, not a Sprint 16 side-quest.
